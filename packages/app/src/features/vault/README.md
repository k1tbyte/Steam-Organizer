# vault

First-run onboarding and the unlock screen. Both render outside the shell (bare routes).

- `useVaultSession` (store) owns the session over `@so/core`: the vaults on this device (`load()`, from IndexedDB), the unlocked vault's key, and the state: `new` (none stored), `locked`, `unlocked`. `unlock(credential, vaultId)` unwraps a key and answers `opened`, `wrong` or `unreadable` (a damaged or newer file), then drops the Steam cache of accounts the vault no longer has (`steamCache.pruneCollections`); `open()` turns the state after the opening animation; `create(name, password)` stores a vault and opens it in one step; `adopt(name, file, password)` does the same with a vault file from elsewhere (a Drive backup), replacing one with its id, and answers like `unlock`; `transact(change)` writes the records `change` returns, read and sealed in one queue with every other write, so none restores an older file; `contents` holds the open vault's records with their data parts opened, `vault` its id and name; `snapshot()` reads its latest file and records in the queue (a backup, an export); `replaceRecords(records)` makes another copy of the open vault its content (a backup restore, a Settings import): records stamped now (accounts edited now too, `restampEdited`, so a sync keeps the restore) and tombstones for what the copy lacks in one `transact` (`services/restoredRecords.ts`), then the restored accounts' held keys drop; `changePassword` rewraps the open vault and `rename(name)` relabels it (in the queue); `remove(id)` deletes a vault from this device after the writes queued before it, and the open one drops its key and Steam cache, so the state turns `locked` or `new`; `lastVaultId` is the vault opened last (kept per device), which the unlock picker offers first; `verify` checks the open vault's password; `lock()` drops the key, after the `onBeforeLock` drafts (a note being typed) have queued their writes. A vault it does not store (mock mode) takes the demo credentials (`demoVerify` in `mocks.ts`): PIN `123456`, password `demo`, Hello waits 1.3s. Its storage half (the stored list, the write queue, `persist`/`save`, the Drive links) is `stores/vaultFiles.ts`; locked accounts' held keys are `stores/recordKeys.ts`.
- Drive sync, the session's side (the engine is `#features/backups`): every change to the file moves the stored `revision` (a rename keeps it), and `StoredVault.sync` links a vault to its Drive copy; `vault.sync` reads `{ syncedAt, pending }`, pending while the copy holds an older revision. `create(name, password, true)` links a new vault with its first push pending, `adopt(..., sync)` links a vault adopted from its copy at revision 0 (a recovery slot added at that unlock is a change to push), `link()` / `unlink()` set and drop the link. `mergeCopy(copy)` merges Drive's copy into the open vault in the queue (`services/vaultSync.ts` over core `mergeRecords` and `newerSlots`; a copy the key can't open throws and writes nothing) and answers the file, a receipt and whether to push; `mergeCopy(null)` only reads the file. `markSynced(receipt, at)` records the copy that took it, refused for a vault removed or linked again since. `onLocked` hands a lock of a linked vault the file it left unpushed, read after the drafts. `unlock(credential, id, copy)` tries the copy's slots when this device's refuse, and keeps the later slots: `useUnlock` fetches the copy after a wrong password, for a linked vault while Drive is connected (silent token only), so a password changed on another device opens here; an answer that comes after leaving the page is dropped with its key. Slots merged from another device with another recovery pair (two devices that each added one) take the session key's recovery half with them.
- Only the app's guard and the popup call `load()`: the autofill entry runs on a Steam page, whose IndexedDB is not ours.
- `tally(contents)` (`services/vaultContents.ts`) counts accounts and those with Steam Guard, for Backups and Settings.
- Vault management on the unlock screen: Add vault opens Welcome (onboarding allows `locked` too, with Back to unlock), Remove from this device asks first (`useRemoveVault`; Drive backups, the synced copy and exports stay), "Forgot it? Reset vault" opens `ResetVaultDialog`. A linked vault shows on the picker as Google Drive, "synced {ago}" once it has synced. Settings opens the same dialog through the facade (`defineAsyncComponent`, so the facade loads no SFC in unit tests). Reset is three steps and a 1.6 s hold (`services/vaultReset.ts`); account and authenticator counts show for the open vault only. With Drive connected it lists the vault's backups by id and, if chosen, deletes those step 1 showed first (a failure keeps the vault, so the hold retries), then removes the vault; the guard moves the page and a toast confirms. A linked vault's synced copy is always deleted with it (listed again at the hold, a copy already gone counts as done), so other devices keep the vault on their own by the copy-gone rule.
- `installVaultGuard(router)` (called by `router.ts`) waits for `load()`, then sends a route to its home by state (`new` -> `/welcome`, `locked` -> `/unlock`, `unlocked` -> `/`) from `meta.vaultAccess`, and moves the open page when the state changes. The shell route allows only `unlocked`.
- Onboarding is one flow with the step in the URL: `/welcome` -> `/welcome/vault` -> `/welcome/password` -> `/welcome/steam`; `/welcome/restore` and `/welcome/import` branch from Welcome; their view-models sit in `composables/onboarding/`. The draft (name, location, master password) lives in `useOnboardingDraft`, provided by `OnboardingLayout`. The Vault step's Google Drive choice signs in through `useDrive()` from the click (`prepare()` first, so the web window is not blocked; Change signs out and in again) and needs the connection; the last step (Steam access) creates the vault, linked to Drive for that choice (its first copy pushes once the shell's sync runs), so leaving the flow earlier stores nothing, and seals the Web API key into its settings record (`withSteamKey`; an incomplete key holds Open accounts, Skip drops it); `useRestore` signs in through `useDrive()` (Switch signs out, so Google offers its account picker), lists every vault's synced copy and backups on that Drive (the latest synced copy first, then backups latest first, Other backups to pick another) and opens the picked one through `adopt`: a synced copy with the vault's master password, linked to that copy (joining from a second device), a backup with the password of its time, kept on this device; `useImportFile` does the same with a `.sovault` export picked from disk, named after the file. Both refuse a vault already on this device: inside it, Backups and Settings restore or import with a warning.
- Unlock: Windows Hello, PIN (desktop keyboard, phone `PinKeypad`) and master password. Three wrong PINs disable the PIN (`services/pinAttempts.ts`). A stored vault lists the master password only until PIN and Hello slots exist.
- `core/passwordStrength.ts` scores the master password (shared with Settings) for the kit `FpSegmentedMeter`.
