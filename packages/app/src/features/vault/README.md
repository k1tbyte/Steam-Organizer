# vault

First-run onboarding and the unlock screen. Both render outside the shell (bare routes).

- `useVaultSession` (store) owns the session over `@so/core`: the vaults on this device (`load()`, from IndexedDB), the unlocked vault's key, and the state: `new` (none stored), `locked`, `unlocked`. `unlock(credential, vaultId)` unwraps a key and answers `opened`, `wrong` or `unreadable` (a damaged or newer file), then drops the Steam cache of accounts the vault no longer has (`steamCache.pruneCollections`); `open()` turns the state after the opening animation; `create(name, password)` stores a vault and opens it in one step; `adopt(name, file, password)` does the same with a vault file from elsewhere (a Drive backup), replacing one with its id, and answers like `unlock`; `transact(change)` writes the records `change` returns, read and sealed in one queue with every other write, so none restores an older file (across pages too, below); `contents` holds the open vault's records with their data parts opened, `vault` its id and name; `snapshot()` reads its latest file and records in the queue (a backup, an export); `replaceRecords(records)` makes another copy of the open vault its content (a backup restore, a Settings import): records stamped now (accounts edited now too, `restampEdited`, so a sync keeps the restore) and tombstones for what the copy lacks in one `transact` (`services/restoredRecords.ts`), then the restored accounts' held keys drop; `changePassword` rewraps the open vault and `rename(name)` relabels it (in the queue); `remove(id)` deletes a vault from this device after the writes queued before it, and the open one drops its key and Steam cache, so the state turns `locked` or `new`; `lastVaultId` is the vault opened last (kept per device), which the unlock picker offers first; `verify` checks the open vault's password; `lock()` drops the key, after the `onBeforeLock` drafts (a note being typed) have queued their writes, and removes the kept entry, so every other page locks. A vault it does not store (mock mode) takes the demo credentials (`demoVerify` in `mocks.ts`): PIN `123456`, password `demo`, Hello waits 1.3s. Its storage half (the stored list, the write queue, `persist`/`save`, the Drive links) is `stores/vaultFiles.ts`; the open vault its halves share (key, records, locked accounts' held keys from `stores/recordKeys.ts`, the lock epoch and the one teardown `close()`) is `stores/openState.ts`; its Drive half (`mergeCopy`, the lock checkpoint `onLocked` hands the sync, the link) is `stores/vaultSyncSide.ts`; its records half (`transact`, `replaceRecords`, `snapshot`, `secretOf`, `withKey`) is `stores/vaultRecords.ts`.
- Drive sync, the session's side (the engine is `#features/backups`): every change to the file moves the stored `revision` (a rename keeps it), and `StoredVault.sync` links a vault to its Drive copy; `vault.sync` reads `{ syncedAt, pending }`, pending while the copy holds an older revision. `create(name, password, true)` links a new vault with its first push pending, `adopt(..., sync)` links a vault adopted from its copy at revision 0 (a recovery slot added at that unlock is a change to push), `link()` / `unlink()` set and drop the link. `mergeCopy(copy)` merges Drive's copy into the open vault in the queue (`services/vaultSync.ts` over core `mergeRecords` and `newerSlots`; a copy the key can't open throws and writes nothing), purges tombstones older than 90 days (`TOMBSTONE_TTL_MS`; a purge alone asks for no push), rekeys accounts left with one order key (`rekeyTies`, stamps kept, a push), and answers the file, a receipt and whether to push; `mergeCopy(null)` merges a file with nothing pending with itself, so a sync with nothing to download still purges, and returns a pending one as is. `markSynced(receipt, at)` records the copy that took it, refused for a vault removed or linked again since, by any page (every link gets a new `sync.linkId`, which the receipt carries). `onLocked` hands a lock of a linked vault the file it left unpushed, read after the drafts. `unlock(credential, id, copy)` tries the copy's slots when this device's refuse, and keeps the later slots: `useUnlockPassword` fetches the copy after a wrong password, for a linked vault while Drive is connected (silent token only), so a password changed on another device opens here (with Drive signed out or expired, a refused password offers "Sign in with Google", which checks it again against the copy); an answer that comes after leaving the page is dropped with its key. Slots merged from another device with another recovery pair (two devices that each added one) take the session key's recovery half with them.
- Hello (`services/device/passkey.ts`, `useVaultSecurity().hello` / `enableHello(password)` / `disableHello()`): the master password is checked, then `navigator.credentials.create` (platform authenticator, `userVerification: 'required'`, `extensions.prf`) and, when the creation returns no PRF result, one `get` with `prf.eval` (a fixed salt per vault id); the 32 bytes wrap the secret as `slot:prf` (`enrollPrf`) and are sealed under `records` as `rearm.prf`, then zeroed. `unlock({ method: 'bio' }, vaultId)` asserts with `allowCredentials: [id]` and opens that slot. Availability is `PublicKeyCredential.getClientCapabilities` `extension:prf` when reported, else its `passkeyPlatformAuthenticator` (Safari reports no extensions and answers `false` to `isUserVerifyingPlatformAuthenticatorAvailable` even with Touch ID), else `isUserVerifyingPlatformAuthenticatorAvailable`; the creation's `prf.enabled` confirms it, and needs an RP ID from `Platform.passkeys` (web: `location.hostname`; Chrome extension: its ID, kept stable by the manifest key; Firefox extension: none, so `hello` is `unavailable`); enrollment and assertions use the same one. A cancelled or failed ceremony is a typed result, never a thrown `DOMException`; a passkey without PRF output is `no-prf` (a password manager's: Bitwarden's extension takes the prompt on web pages, never on the extension's own, and gives no PRF), so it never becomes a slot. The popup does not offer it: a platform dialog may close the popup, so it restores a kept session or takes the password. The slot follows Master password after restart like the PIN's (`armAfterPassword` builds it again). `useHelloLabel()` replaces every hard-coded "Windows Hello" and "Fingerprint".
- PIN (`stores/useVaultSecurity.ts`, `services/device/pinSlots.ts`, `services/device/deviceSlots.ts`): `setPin(password, pin)` moves the secret from the password slot under PBKDF2(6 digits, its own salt, 600k) (`enrollPin`, one PBKDF2 over the PIN) and seals the PBKDF2 bits under `records` as `rearm.pin`; `removePin()` asks nothing; `pin` reads `off`, `on` or `paused`. `unlock({ method: 'pin', pin }, vaultId)` tries the slot inside a Web Lock named for the vault, which is held over re-reading the count, trying the PIN and saving the count, so two pages share one budget of three; at three it answers `wrong` without trying, a right PIN or a master-password unlock resets the count. A password change never touches the slot: the secret stays. With Master password after restart on the slot lives in the session area (the extension) or in page memory (the web), and a master-password unlock rebuilds it from `rearm.pin` (`armAfterPassword`); toggling it moves the slots at once (`session.policyChanged(previous)`). A demo vault (mock mode) counts its PINs in memory.
- Lock policy and kept session. `useLockPolicy()` holds Lock after and Master password after restart per device (`so:security`, `LockAfter` in `model.ts`); its setters move the kept session at once (`session.policyChanged()`), with no password. Every unlock (`openWith`, the one way in) reseals the secret under the device key (`sealForDevice`, `deviceStore.key()`: random, non-extractable, in its own IndexedDB) and the session holds that ciphertext. `stores/keptSession.ts` puts it where the policy says: Immediately nowhere (`useAutoLock` locks the page when it is hidden or closed), 1 minute to 4 hours in the session area beside a shared `lastActive`, On browser restart there without a timer, Never also in `deviceStore` (the session area only with Master password after restart). The entry in the session area is the live signal under every policy: `load()` restores a kept session before the guard decides (a failure drops it and stays locked) and watches the entry for the life of the session, locked or not, so another page's lock locks this one and another page's unlock restores a locked one. `useAutoLock()` (once per page, from `AppShell`, the popup frame and the autofill vault host) writes `lastActive` at most every 15 s from pointer, key, wheel and touch, and locks at the deadline after reading the shared stamp again. It returns `check()` (policy and stamp read again, locks past the deadline, resolves once decided) and `touch()` (the same throttled stamp as a pointer event: a fill the host hands out counts as activity); `useAutoLock({ hidden: true })` is for a page never visible (the host), where Immediately holds it locked, also when the policy is switched while it runs. `Platform.session` is the area (`core/session/sessionArea.ts`): the extension's `storage.session`, the web's per-tab `sessionStorage` (it survives a reload but may come back with a restored tab, so On browser restart lasts until the tab closes there), memory in tests. `remove(id)` clears the vault's device slots too. Only the app's guard, the popup and the vault host call `load()`: the autofill entry runs on a Steam page, whose IndexedDB is not ours, so it stays out and asks the host instead. One writer across pages (`stores/vaultFiles.ts`): every write of the queue holds the Web Lock `so:vaults` (`acrossPages` from `#core`) and first reads the stored vaults, so it lands on what another page stored and `revision` never repeats, and the open vault follows that file before the write; each stored change posts the vault id on the `BroadcastChannel` `so:vaults`. A page that loaded the list answers with `refresh()`: in its own queue but outside the lock (a read never stalls another page's write), the list takes in what was added, changed or removed, and the open vault follows (`vaultRecords.follow`): a new file opens again with the held key and only the records whose secret changed (an account password set, changed or removed there) drop their held keys, and the key takes the file's recovery pair when another page added or merged one (an open does the same: its key may come from an older file); a rename, a link or a password change keep the records; a vault removed, or a file the held key no longer opens, locks the page. A page that may have slept through the messages (the vault host) calls `session.refreshOpen()` before it uses the open vault (one IndexedDB read when unchanged). A write never waits on the slots lock, and a slots holder never on a write. Another page's unlock restores here only after `files.refresh()` took in the vaults and files that page stored since this one loaded; a restore that finishes after another page locked reads the entry again and locks (or restores the vault opened meanwhile), and a restored page keeps the idle deadline it found. A lock drops the copy on disk before the entry, so a page loading meanwhile restores from the entry and locks with it; an unlock answer that began before a lock never opens.
- `sessionBound` (`services/device/keptEntry.ts`): values that end with the open session (autofill's last fill per tab). They sit in the session area, indexed, and `removeKept` removes them with the kept entry, so every lock clears them whichever page made them.
- `tally(contents)` (`services/vaultContents.ts`) counts accounts and those with Steam Guard, for Backups and Settings.
- Vault management on the unlock screen: Add vault opens Welcome (onboarding allows `locked` too, with Back to unlock), Remove from this device asks first (`useRemoveVault`; Drive backups, the synced copy and exports stay), "Forgot it? Reset vault" opens `ResetVaultDialog`. A linked vault shows on the picker as Google Drive, "synced {ago}" once it has synced. Settings opens the same dialog through the facade (`defineAsyncComponent`, so the facade loads no SFC in unit tests). Reset is three steps and a 1.6 s hold (`services/vaultReset.ts`); account and authenticator counts show for the open vault only. With Drive connected it lists the vault's backups by id and, if chosen, deletes those step 1 showed first (a failure keeps the vault, so the hold retries), then removes the vault; the guard moves the page and a toast confirms. A linked vault's synced copy is always deleted with it (listed again at the hold, a copy already gone counts as done), so other devices keep the vault on their own by the copy-gone rule.
- `installVaultGuard(router)` (called by `router.ts`) waits for `load()`, then sends a route to its home by state (`new` -> `/welcome`, `locked` -> `/unlock`, `unlocked` -> `/`) from `meta.vaultAccess`, and moves the open page when the state changes. The shell route allows only `unlocked`.
- Onboarding is one flow with the step in the URL: `/welcome` -> `/welcome/vault` -> `/welcome/password` -> `/welcome/steam`; `/welcome/restore` and `/welcome/import` branch from Welcome; their view-models sit in `composables/onboarding/`. The draft (name, location, master password) lives in `useOnboardingDraft`, provided by `OnboardingLayout`. The Vault step's Google Drive choice signs in through `useDrive()` from the click (`prepare()` first, so the web window is not blocked; Change signs out and in again) and needs the connection; the last step (Steam access) creates the vault, linked to Drive for that choice (its first copy pushes once the shell's sync runs), so leaving the flow earlier stores nothing, and seals the Web API key into its settings record (`withSteamKey`; an incomplete key holds Open accounts, Skip drops it); `useRestore` signs in through `useDrive()` (Switch signs out, so Google offers its account picker), lists every vault's synced copy and backups on that Drive (the latest synced copy first, then backups latest first, Other backups to pick another) and opens the picked one through `adopt`: a synced copy with the vault's master password, linked to that copy (joining from a second device), a backup with the password of its time, kept on this device; `useImportFile` does the same with a `.sovault` export picked from disk, named after the file (a partial export of picked accounts is refused: it imports into an open vault). Both refuse a vault already on this device: inside it, Backups and Settings restore or import with a warning.
- Unlock: Hello (named by `useHelloLabel()` after the OS: Windows Hello, Touch ID, Fingerprint on Android, else Passkey), PIN (desktop keyboard, phone `PinKeypad`, which carries Hello as a key; a phone vault with Hello and no usable PIN shows `UnlockHello` alone, with a link to the password) and master password. Three wrong PINs disable the PIN (`services/device/pinAttempts.ts`). A stored vault lists the PIN while it has a PIN slot on this device (`session.device`: `DeviceFacts` per vault id, never a slot or a key), paused or not, and the wrong tries come from there, so a reload or another page never resets them; the popup takes the password only.
- `core/passwordStrength.ts` scores the master password (shared with Settings) for the kit `FpSegmentedMeter`.
