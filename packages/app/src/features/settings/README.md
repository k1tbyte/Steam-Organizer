# settings

Desktop: a 960x660 window over the app (`?settings=<section>`, `useQueryOverlay`), nav on the left, the section on the right. Phone: the Settings tab shows the index, a section opens as its own screen (`/settings/:section`, no tab bar). Crossing the `lg` breakpoint carries the open section over (`useSettingsLayoutSync`).

- `registry.ts` lists the sections in nav order; `useSettingsSections` adds their copy. A section is `sections/<name>/<Name>Section.vue` plus its `use<Name>Section.ts` view-model, registered in `sections/index.ts`; Bots is listed as Soon and shows `SectionPending`.
- Appearance is complete and real: `sections/appearance/` drives the nine knobs of `core/appearance` (`.claude/rules/appearance.md`). The background picture stays in `localStorage` for now and moves to IndexedDB later; only `core/appearance/background.ts` changes.
- Tags is real: `sections/tags/` reads and writes through `useVaultTags` from `features/accounts` (rename, recolor, New tag, delete with Undo; a used tag asks first), and shows the accounts sample's tags with no vault open. Fields is real: `sections/fields/` drafts a placement over `useFieldPlacement` from accounts and moves every account's fields on Apply (progress, done, Finish after an interrupted move; `services/fieldSecrecy` holds the fixed fields and the moves). Linked services is real the same way: `sections/services/` over `useVaultServices` from `features/linked-services` (New service, rename, SVG icon upload or removal, delete with Undo, the built-in set read-only). Both name rows in place with `components/NameField.vue`.
- Steam's Web API key is the vault's (`useSteamKey` from `features/steam`, `sections/steam/useSteamKeyField.ts`): saved once the field is empty or holds a whole key, then checked against Steam for the Works mark or the reason it fails. The phone index reads the same key. Below it the store currency (`useSteamCurrency`), every Steam currency named by `Intl.DisplayNames`.
- Vault is real: the open vault's name, home (Google Drive for a synced vault) and account count (`useVaultSession`, `tally` from `features/vault`), Rename in place with `NameField`, Export and Import (`ExportVaultDialog`, `useImportVault` with `ImportVaultDialog` from `features/accounts`, the same dialogs as the Accounts toolbar: this vault's file replaces it, a partial file or the old app's export adds accounts), and Reset vault opens `ResetVaultDialog` from the vault feature.
- Steam's site access is the one section built on a mock. What the user edits (site grants) lives in `stores/settingsStore.ts`, so the sections and the phone index read the same values; it moves to its owner when wired. Security is real: its lock timeout, Master password after restart, PIN and Hello are real: `useLockPolicy()` and `useVaultSecurity()` from `#features/vault`, kept per device. Data other features own is read through `composables/sources/` (one composable per source, the only readers of `mocks.ts`). The Drive backup count on the Sync line is `useBackupCount()` from `#features/backups`.
- Security is the one section with separate phone markup (`SecurityMobile`, the mockup's grouped cards); the others reflow through `FpFormRow` (`inline` keeps a switch beside its label on phones).
- `dialogs/hello/` (Turn on Hello: confirm the master password, then the platform's prompt, through `useEnableHello` over `useVaultSecurity().enableHello`; the switch turns it off directly, and is disabled with "Not available on this device" where `hello` is `unavailable`; a passkey without PRF output, as a password manager such as Bitwarden makes, is refused with a line to save it with Hello on this device instead), `dialogs/pin/` (Set a PIN / Change PIN: the master password, then 6 digits twice with `FpPinInput`; `useSetPin` over `useVaultSecurity().setPin`, closed through `useCloseOnSuccess`; the phone's PIN switch opens it to turn the PIN on and removes it to turn it off, Remove asks nothing), and `dialogs/password/` (Change master password, opened from Security) are bound to an action in flight, so local state and not URL overlays; each restarts its flow when it opens. Change master password takes the master password, the new one with its strength and its repeat from `PasswordFields` (`components/PasswordFields.vue`, over `usePasswordFields` from `#core`, shared with the vault export).
- The nav footer (and the phone index's last line) shows the running version through `useAboutApp`: `APP_VERSION` from `#core`, read from the root `package.json`, the one product version (the extension manifest takes it too). On web a build waiting to take over (`useAppUpdate` from `#core`) adds "Update to 3.0.2" to the desktop footer; a click reloads into it. An extension shows the version only: its browser updates it.
- `services/` holds the framework-free rules with tests: `fieldSecrecy`. The password rules and strength (`core/passwordStrength.ts`) are shared with onboarding and the export.
- The shell calls `useSettingsEntry()` (`open(section?)`) and provides it as `useSettingsLink()` (`#core`), which features link into a section with: settings imports them (Tags reads accounts, Linked services reads linked-services), never the reverse; the facade exports `SettingsHost`, `useSettingsEntry`, `settingsRoutes` and `SectionKey`. `SettingsHost` loads the window, sections included, as its own chunk on the first desktop open.

## Mocks

Mockup: `Settings.dc.html` (Settings · Desktop, Settings · Mobile, Settings · Mobile · Security, Change master password · Dialog).

| Mock (variants) | UI built | Source | Wire in |
|---|---|---|---|
| `settings.steam` (Firefox, Chromium all allowed, Nothing allowed) | site Allowed / Allow, Firefox note | browser site permissions and the browser kind (`Platform` has none yet) | `sources/useSteamAccess` |

Local state until the owner exists: the allowed sites (`stores/settingsStore.ts`); it starts empty and is not persisted. Security is wired: Lock after and Master password after restart persist per device (`useLockPolicy`; a change moves the kept session at once, without a password), the PIN and Hello are slots of the open vault read through `useVaultSecurity`. Sync & backup is real: Auto sync, its interval and Auto backup are the backups engine's (`useVaultSync` from `#features/backups`, kept per device), the status line reads `useSyncStatus` (`sources/useDriveSync.ts`), and Sync now shows for a synced open vault.

Unwired intents: the site Allow buttons (they only mark a local list, no browser permission is requested). Change master password rewraps the open vault through `useVaultSession().changePassword`; with no real vault open it takes the demo `demo`.
